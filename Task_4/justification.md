# Обоснование конфигурации инфраструктуры
## 1. Архитектурное обоснование выбора ресурсов и параметров

Основной целью проекта являлось проектирование и локальное тестирование масштабируемого слоя обработки данных (Data Lake) и интерфейса интеграции (API Gateway). Выбранный стек сервисов эмулирует современные Cloud-Native подходы:

*   **AWS API Gateway**: Выбран в качестве единой точки входа (API Management Layer) для внешних запросов и систем-источников логов. Локально настроен REST API с методом `GET` и Mock-интеграцией, что позволяет изолированно тестировать маршрутизацию и форматы ответов без развертывания тяжелого бэкенда.
*   **AWS S3 (Data Lake Storage)**: Выбран в качестве основного недеструктивного хранилища сырых данных (`my-local-datalake`). S3 является стандартом де-факто для построения Data Lake благодаря низкой стоимости хранения и высокой пропускной способности. Дополнительно выделен изолированный бакет `my-local-athena-results` для атомарного сохранения результатов аналитических выборок.
*   **AWS Glue Catalog & AWS Athena**: Интегрированы для реализации концепции **Schema-on-Read** (схема при чтении). Glue Data Catalog управляет метаданными и описывает структуру CSV-файлов, хранящихся в S3. Athena выполняет распределенные SQL-запросы к сырым данным «на лету», используя встроенный высокопроизводительный движок DuckDB внутри локального эмулятора.
*   **AWS IAM (Identity and Access Management)**: Безопасность заложена на уровне проектирования (Security by Design). Создана выделенная роль `execution-role` с минимально необходимым набором прав (Least Privilege Principle) для логирования и взаимодействия компонентов, исключая использование административных учетных записей.

## 2. Специфика локального окружения: Отказ от виртуальных машин, дисков и NAT

При проектировании архитектуры данного проекта было принято решение отказаться от использования низкоуровневых инфраструктурных компонентов (IaaS), таких как виртуальные машины (EC2), сетевые блочные диски (EBS) и выделенные NAT-шлюзы. Выбор симулятора **MiniStack** в качестве среды исполнения накладывает следующие жесткие архитектурные ограничения и компромиссы (trade-offs):

1.  **Контейнерная природа и отсутствие виртуализации (EC2)**: 
    MiniStack функционирует как легковесный процесс внутри Docker-контейнера в пространстве пользователя (User Space). У него нет доступа к аппаратному гипервизору хост-машины (KVM/Intel-VT). Эмуляция полноценной операционной системы (виртуальной машины) потребовала бы вложенной виртуализации (Nested Virtualization), что увеличило бы потребление RAM с **~30 МБ до десятков Гигабайт** и лишило бы проект мобильности. Вычислительные ресурсы (Compute) в проекте симулируются на уровне сервисов (API Gateway), что достаточно для проверки бизнес-логики.
2.  **Абстракция файловой системы вместо блочных устройств (EBS)**:
    Настоящий диск AWS EBS является сетевым блочным устройством, монтируемым к ядру ОС. В контейнерной среде MiniStack работа с постоянными данными ограничена абстракцией Docker Volumes (монтированием директорий хоста). Создание, форматирование в ext4/XFS и динамическое переподключение «сырых» дисков технически невозможно и избыточно для тестирования Data Lake, работающего поверх объектного хранилища S3.
3.  **Плоская сеть Docker вместо топологии с NAT-шлюзами**:
    В промышленном облаке NAT-шлюз необходим для изоляции ресурсов в приватных подсетях VPC и обеспечения им безопасного контролируемого выхода в интернет. Локальная лаборатория развернута внутри изолированной bridge-сети Docker (`tf_network`). Все участники сети находятся в едином плоском адресном пространстве и используют сетевой стек хост-машины (Ubuntu) для связи с внешним миром. Имитация таблиц маршрутизации (Route Tables) и трансляции адресов (NAT) внутри Docker-сети усложнила бы конфигурацию, не принеся практической пользы для тестирования логики Terraform.

## 3. Причины использования декларативного подхода

Для управления инфраструктурой проекта был выбран инструмент **Terraform**, реализующий **декларативный подход** (описание целевого состояния системы, а не шагов по его достижению). Основные причины выбора:

*   **Идемпотентность (Idempotency)**: Гарантирует, что повторные запуски команды `terraform apply` не приведут к созданию дубликатов ресурсов, изменению работающих систем или ошибкам `EntityAlreadyExists`. Terraform сверяет текущую конфигурацию файлов с реальным состоянием среды и вносит изменения только при обнаружении расхождений (Configuration Drift).
*   **Автоматическое построение графа зависимостей (Dependency Graph)**: Архитектору не нужно вручную прописывать последовательность создания ресурсов. Terraform самостоятельно понимает, что база данных Glue должна быть создана строго после S3-бакета, а метод API Gateway — после самого шлюза.
*   **Декларация как документация**: Файлы проекта (`main.tf`, `variables.tf`) в явном виде описывают финальную архитектуру. Любой инженер, открыв код, сразу видит структуру Data Lake и настройки прав, без необходимости разбираться в императивных многострочных bash-скриптах или вызовах `curl`.

## 4. Роль IaC в воспроизводимости и масштабируемости инфраструктуры

Концепция **Infrastructure as Code (IaC)** переводит управление аппаратными ресурсами в плоскость разработки программного обеспечения, обеспечивая два ключевых свойства системы:

### Воспроизводимость (Reproducibility)
*   **Изоляция сред через параметризацию**: Разделение конфигурации (`main.tf`) и данных (`terraform.tfvars`) позволяет разворачивать идентичные копии инфраструктуры. Изменяя лишь переменные, данный код можно применить как локально в MiniStack, так и в тестовом контуре (Stage) или в продуктивном облаке (Prod).
*   **Фиксация состояния (State Lock & Versioning)**: Использование файла блокировок (`.terraform.lock.hcl`) жестко закрепляет версии провайдеров. Это гарантирует, что инфраструктура будет развернута одинаково вне зависимости от того, запускается она на машине разработчика или в изолированном CI/CD-пайплайне.

### Масштабируемость (Scalability)
*   **Модульность**: Созданная конфигурация Data Lake (S3 + Glue + Athena) может быть инкапсулирована в многоразовый Terraform-модуль. При необходимости создать аналитические зоны для 20 различных департаментов компании, код не копируется вручную — создается цикл, вызывающий этот модуль с новыми параметрами.
*   **Скорость и автоматизация**: Масштабирование инфраструктуры (например, добавление новых таблиц в каталог или новых эндпоинтов в API) происходит декларативно через списки и циклы (`for_each`). Развертывание сотен взаимосвязанных ресурсов занимает минуты и полностью исключает человеческий фактор (ошибки ручного кликанья в веб-интерфейсе облака).
